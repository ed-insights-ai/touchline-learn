## The idea

A language model is good at writing and unreliable at arithmetic and recall. A
trustworthy system uses it for the first and fences it off from the second.
Touchline calls that fence the determinism boundary.

## How Touchline does it

- **Collection uses no model at all.** Fetching, proving, parsing, resolving
  and building are ordinary code. Run them twice on the same input and the
  output is identical. That is what makes them testable.
- **Code computes every number.** Before any prose is written, a program
  computes a digest: season form, scoring patterns, head-to-head history and so
  on. The rule is stated in the code: if a figure is not in the digest, the
  report cannot say it.
- **The model fills named slots.** Its output is a file with a fixed shape: a
  headline, a bottom line, a set number of findings. The page layout, the
  tables and the charts are produced by code from the digest. The model's text
  is placed into its slots.
- **A gate follows every generative step.** The model declares that it is
  finished, and a validator decides whether that is true. Validators count
  files, check shapes, compare claims with the data, enforce word limits, and
  reject text that mentions internal machinery. On the website, every journal
  claim carries a `basis`, and the validator drops what it cannot recompute.

## Example

A report loop once ended because the model replied that all teams were
researched, when some were not. The fix was not a better prompt. It was a check
that counts the research files and compares the count with the number of teams,
on every pass. The model's word is no longer what ends the loop.

## Terms

Determinism, reproducibility, grounding, hallucination, structured output,
human-in-the-loop versus validator-in-the-loop, guardrail, separation of
computation and narration.

## Questions

1. Where exactly is the boundary in a system you have built with a language
   model? Which side computes the numbers?
2. A narrative can pass every gate and still be wrong. What do shape checks
   prove, and what do they not prove?
3. Why is a receipt naming the dataset version part of an honest answer?

## Lab: recompute every number in a draft

```bash
python labs/m09_claims.py
```

`labs/data/journal_draft.json` is a drafted journal for the sample's 2026
men's season, in the shape a model would be asked to return: a headline and a
list of claims, each naming its `basis`. No model is called, so the lab gives
the same result every time. Some claims are wrong on purpose.

```
keep  Alder Ridge won nine of its conference games.
      recomputed 9
...
DROP  Cedar Grove lost eight times.
      claimed 8, recomputed 7
DROP  St. Lambert has completed all 14 of its conference games.
      claimed 14, recomputed 12
keep  Carlos Burke leads the league with six goals.
      recomputed 6
DROP  The Herons are playing with real confidence.
      no basis: nothing to recompute
DROP  Brightwater State averaged 412 fans a game.
      'average_attendance' is not in the digest, so the journal cannot say it

4 kept, 4 dropped
```

Four different failures, one response. A wrong number, a number that ignored
the counting rule, a sentence with nothing behind it, and a figure the digest
never computed are all dropped. A dropped claim is the system working.

Then the lab shows the limit of what it just did:

```
A claim that passed and is still misleading: 'leads the league' is shared by 2 players:
  [('HTU', 'Carlos Burke'), ('HTU', 'Devin Galloway')]
The validator proved the number. It did not prove the sentence.
```

The six goals are correct. "Leads the league" is not quite: two players have
six. The claim fits its contract and still says more than the data shows, which
is why Touchline keeps its claims close to their figures.
