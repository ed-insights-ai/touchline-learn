## The idea

A pipeline is also an organization of code, permissions and money. Where each
piece lives decides who can change it, who can see it, and what breaks when it
changes.

## Why split it this way

- **The recipe is the secret.** Any single season's scores are public on the
  schools' sites. What is hard to reproduce is the registry and the knowledge
  of a thousand sites' quirks, plus ten years of archive. So the collector and
  the data are private, and everything else can be open.
- **Data in version control.** Each daily run is a commit in a data home. That
  gives a full history, a diff of what changed each day, and an undo. It also
  means "which data built this site?" has an exact answer: a commit id.
- **Public code tests on public data.** Because the contracts repository holds
  a sample in the real shape, the website can be developed, tested and reviewed
  without access to the dataset. This site does the same thing
  with its own invented sample.
- **Pinned versions.** The daily workflow uses a recorded, exact version of the
  code it builds with. A change reaches production only when someone moves that
  pin on purpose. You will know this as
  dependency pinning, here applied between a team's own repositories.

## How the repositories stay in step

| Mechanism | What it does |
|---|---|
| Contracts | Every file carries a version tag. The collector checks its real output against the contract before uploading anything, so every consumer can rely on the shape. |
| One shared sample | The open repositories never see the full dataset. They build and test on the same small sample. |
| Fixed versions | A change in build code reaches production only when the recorded version is moved on purpose. |
| Agreement check | Two independent implementations compute the same figures. Each day the workflow compares team records from both, and a disagreement holds back the release. |
| One-way keys | Only the private collector can write to the data homes and the cloud. Public repositories hold no keys, so nothing a stranger submits can reach the data. |
| Signature | The published database is signed with a key that never leaves the cloud. A receiver checks the signature with the matching public key. |

## Automation

A scheduled workflow runs the steps in order: collect, check, build, publish,
release. Each job starts only if the one before it succeeded. If one collection
job fails, its schools are a day stale, an alarm says so, and the rest still
publishes.

## Security, in four rules

1. **No long-lived cloud keys.** The workflow proves its identity to the cloud
   provider with a short-lived token, and receives temporary credentials
   limited to one job.
2. **Least privilege.** The job that deploys the site can write to the site's
   storage and nothing else. It cannot read the dataset.
3. **Public repositories hold no secrets,** so a contribution from a stranger
   cannot reach the data.
4. **Privileged steps run only from the reviewed main branch.**

## Cost

Static files and object storage are cheap, and the design leans on that.
Hosting the site, the dataset and the archive costs a few dollars a month. The
largest running cost is the model that writes journals, so that step is batched
and only runs for conferences that played.

## Terms

Orchestration, DAG (directed acyclic graph of jobs), CI/CD, dependency pinning,
least privilege, workload identity federation (OIDC), secrets management, data
versioning, monorepo versus polyrepo.

## Lab: the daily run as a graph

```bash
python labs/m10_jobgraph.py
```

The lab describes the daily run as seven jobs. Each job names what it needs,
what it waits for but can live without, what it touches, and what its
credentials allow.

```
Order of work
collect-first -> collect-second -> contract-check -> bundle -> snapshot -> site -> release

Least privilege
jobs holding a permission they never use: none
can the site deploy job read the dataset? False
```

Then it replays the day with one job failing:

| What fails | What happens |
|---|---|
| Nothing | Everything runs and today's data is released |
| `collect-second` (one collection job) | The contract check runs and reports those schools stale. The release still goes out. |
| `contract-check` | Everything after it is skipped. Yesterday's release stays in place. |
| `site` | The snapshot was built, but the release is skipped: the pointer moves only when every gate has passed. |

The difference between the second row and the third is the difference between
a soft dependency and a gate. Try your own:

```bash
python labs/m10_jobgraph.py --fail snapshot
```
